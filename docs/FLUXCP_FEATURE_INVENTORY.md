## How to read this document

Legacy FluxCP has no router. `index.php` boots the app and hands control to `Flux_Dispatcher`, which maps a `module` + `action` pair onto two files:

```
modules/<module>/<action>.php          -> controller logic (sets variables)
themes/<theme>/<module>/<action>.php   -> view (renders those variables)
```

Both files run in the scope of `Flux_Template`, so `$this` inside an action is the template object. A request is therefore addressed as `?module=<m>&action=<a>`, or `/<m>/<a>` when `UseCleanUrls` is enabled.

Column meanings:

| Column | Meaning |
| --- | --- |
| **Action** | The `action` value; file is `modules/<module>/<action>.php`. |
| **LOC** | Lines in the legacy action file — a rough proxy for porting effort. |
| **Access** | Level from `config/access.php`. `UNLISTED` means no entry exists. |
| **Databases / tables** | `login:`, `charmap:`, `logs:` = rAthena connections; `cp:` = FluxCP-owned table referenced via the `FluxTables` config map. |
| **Feature gates** | `$auth->allowedTo*` checks performed inside the action. |
| **View** | Default-theme template, or `(none)` if the action renders nothing. |

`UNLISTED` is significant: `Flux_Authorization::actionAllowed()` returns `-1` when no access key exists, and `Flux_Dispatcher` only blocks when the result is strictly `false`. Unlisted actions are therefore reachable by anyone. See [MIGRATION_DECISIONS.md](MIGRATION_DECISIONS.md) for how the port handles this.
